# 업종 특화 멀티앱 전략 — 마케팅 & 개발 (2026-07-29)

> 선행 문서: [`industry-feature-mapping-2026-07-29.md`](./industry-feature-mapping-2026-07-29.md)
> (업종별 기능 필요성 조사 — 이 문서의 근거 자료)

## 0. 방향성 요약

현재 DTS는 "불특정 업종이 가입해 조직을 만드는" 범용 스케줄러다. 이 구조를 유지하되,
**하나의 코드베이스 위에 업종별 브랜드/랜딩페이지/온보딩 프리셋을 얹은 여러 개의
"버티컬 앱"으로 마케팅**한다. 백엔드·관리자콘솔·핵심 로직은 공유하고, 사용자가 마주치는
첫인상(브랜드명, 카피, 기본 설정)만 업종에 맞춰 분기한다.

**하지 않을 것**: 업종별 코드 포크, 업종별 별도 DB 프로젝트, 업종별 별도 개발팀 운영.
이는 유지보수 비용을 앱 개수만큼 곱하고, 프로젝트의 "다이나믹 구현 원칙(하드코딩 금지)"과
정면으로 충돌한다.

---

## 1. 왜 지금 이 방향이 맞는가 (근거)

- 범용 "팀 스케줄러"는 잠재 고객이 자신의 문제와 즉시 연결하기 어렵다. 업종명이 들어간
  카피("PT 회원권 관리", "학원 수강권 관리")는 검색 의도·광고 전환율·첫인상 신뢰도에서
  범용 카피보다 유의미하게 유리하다 (Booksy=뷰티, Mindbody=피트니스와 동일한 패턴).
- 이전 분석에서 확인했듯, 레슨권 기능은 12개 세부업종 그룹 중 **4곳 내외에서만 표준적으로
  필요**하다 (PT, 학원·튜터, 요가·필라테스, 골프·무술). 이 그룹은 이미 "이용권/횟수권"이라는
  결제 언어를 쓰고 있어 온보딩 카피를 그대로 재활용할 수 있다 — 첫 버티컬로 가장 마찰이 적다.
- `tenant_mode`("회원개별") 기반 자동 UI 숨김 로직(`adminIsFreeform` 패턴)이 이미 존재해,
  같은 방식을 확장하면 업종별 UI 축소를 큰 리아키텍처 없이 구현할 수 있다.

## 2. 1차 타겟 버티컬 선정

| 후보 | 레슨권 적합도(이전 분석) | 결제 언어 재사용성 | 온라인 마케팅 채널 성숙도 | 채택 |
|---|:---:|:---:|:---:|:---:|
| PT/피트니스 + 요가·필라테스 + 골프·무술 | 🟢 | 높음(회차권 공통어) | 매우 높음(인스타/블로그/커뮤니티) | **1차 채택** |
| 학원·교습소·튜터 | 🟢 | 높음(수강권 공통어) | 높음(맘카페/학원연합회) | 2차 확장 후보 |
| 뷰티(미용실·네일·스파) | 🔴 | 낮음 | 매우 높음 | 보류 |
| 의료·행정·소매 등 | 🔴 | 낮음 | 다양 | 보류 |

**1차 타겟: "PT·요가·필라테스·골프·무술" 통합 — 가칭 "레슨워크(LessonWork)" 또는 "레슨온(LessonOn)"
류의 브랜드로 스포츠 레슨/횟수권 관리 특화 앱.**

이유: (a) 레슨권 기능이 이미 완성돼 있어 추가 개발 없이 바로 셀링포인트로 쓸 수 있음,
(b) 강사 개인 사업자·소규모 스튜디오가 많아 의사결정자(=사용자=구매자)가 1인이라 영업 사이클이
짧음, (c) 인스타그램/블로그 기반 마케팅이 이미 검증된 채널.

## 3. 마케팅 전략

### 3-1. 포지셔닝 & 카피

- 기존: "다중 조직과 스케줄을 한 곳에서" (범용, 카테고리 불명확)
- 신규 버티컬: **"회원 횟수권 소진율까지 챙기는 PT·요가·필라테스 스케줄 관리"**
  - 핵심 후킹 포인트는 범용 스케줄이 아니라 **레슨권 만료 임박 알림 SMS**(이미 구현된 기능,
    README 참조) — "회원이 끊길 뻔한 걸 문자 한 통으로 막았다"는 구체적 시나리오가
    범용 스케줄러보다 훨씬 강한 카피 소재다.
  - 부가 후킹: 강사별 스케줄 개별 관리(회원개별 모드), 역할별 색상 구분(indicator_bar).

### 3-2. 채널 전략

| 채널 | 활용 방식 |
|---|---|
| 인스타그램/블로그 | PT·요가 강사 대상 "회원 관리 꿀팁" 콘텐츠 마케팅, 실제 화면 캡처 포함 |
| 네이버 카페/커뮤니티 | 필라테스·요가 강사 커뮤니티, 헬스 트레이너 커뮤니티에 사용 후기/무료체험 안내 |
| 검색 키워드(SEO/광고) | "PT 회원 관리 앱", "요가 수강권 관리", "필라테스 예약 프로그램" 등 롱테일 키워드 |
| 제휴 | 요가/필라테스 강사 자격증 교육기관, 피트니스 프랜차이즈 본사와의 제휴 입점 |
| 무료체험 → 유료전환 | Basic 플랜 무료 체험 기간을 버티컬별로 다르게 설계(예: 1인 강사는 더 긴 무료 기간) |

### 3-3. 랜딩페이지/앱 노출 전략

- 별도 서브도메인 또는 별도 랜딩페이지(예: `lesson.dtschedule.com` 또는 완전히 다른 브랜드
  도메인) — 가입 CTA는 기존 DTS 회원가입/조직생성 플로우로 연결하되, **온보딩 진입 시점에
  버티컬 값을 쿼리 파라미터/딥링크로 전달**해 조직 생성 시 자동으로 업종 프리셋이 적용되게 함.
- 스크린샷·후기는 실제 레슨권 관리 화면 위주로 구성(범용 스케줄 그리드보다 레슨권 소진 현황,
  만료 알림 발송 화면을 전면에 배치).
- 앱스토어/플레이스토어에 별도 리스팅이 필요한 경우(PWA를 네이티브 래핑한다면), 리스팅명·
  아이콘·설명만 버티컬별로 분리하고 실제 빌드는 동일 코드베이스에서 브랜드 설정만 주입.

### 3-4. 초기 검증 지표 (마케팅)

- 랜딩페이지 → 가입 전환율
- 가입 → 조직 생성 완료율 (프리셋이 실제로 온보딩 마찰을 줄이는지 확인)
- 레슨권 기능 실사용률(가입 후 4주 내 `lesson_package_types` 1개 이상 등록 비율)
- 첫 유료 전환까지 걸리는 기간(범용 버전 대비 단축 여부)

핵심 규칙: **버티컬 간 차이는 전부 설정(데이터)이어야 하며, 코드 분기(if 업종 === 'X')가
되어서는 안 된다.** 이는 이미 CLAUDE.md에 명시된 "다이나믹 구현 원칙"과 동일한 기준이다.

### 4-2. 필요한 기술적 선행 작업

이전 분석 문서 7장의 옵션 1·2를 결합한 형태를 권장한다.

1. **`tenants.settings`에 기능 플래그 확장**
   ```json
   { "feature_flags": { "lesson_packages": true, "autoassign": false } }
   ```
   `AdminPage.tsx`의 `adminIsFreeform` 필터 패턴을 그대로 확장해 `TAB_LABELS` 필터 조건에
   `feature_flags` 체크를 추가한다 (기존 로직 재사용 — 신규 로직 아님).

2. **버티컬 프리셋 테이블/맵 추가**
   가입 온보딩(Setup Wizard)에서 버티컬 값(예: `vertical=lesson-sports`)을 받으면:
   - `tenant_mode` 기본값(예: `회원개별`)
   - 기본 역할 세트(예: "강사", "회원")
   - 기본 커스텀 필드(예: "보유 레슨권", "특이사항")
   - `feature_flags` 기본값(레슨권 on, 자동배정 off 등)
   을 자동 적용. 이미 `wizardModeRecommendation.ts`가 업종→모드 추천을 하고 있으므로,
   같은 파일/패턴을 "업종→프리셋 전체"로 확장하면 된다.

3. **브랜드 설정 레이어**
   앱 이름·로고·테마 프리셋·랜딩 카피를 환경 변수 또는 빌드 타임 설정(`vertical.config.ts`
   같은 단일 파일)으로 분리해, 배포 시점에 어떤 버티컬로 빌드할지만 결정하게 한다.
   (PWA `manifest.webmanifest`의 이름/아이콘도 이 설정에서 파생.)

4. **슈퍼관리자 콘솔에 버티컬별 필터/통계 추가**
   `OrgDrawer.tsx`/`HubMain.tsx`에 조직의 `business_type` 및 적용된 `feature_flags`를
   표시하고, 필요 시 슈퍼관리자가 개별 조직 단위로 오버라이드할 수 있는 토글 UI 추가.

### 4-3. 하지 말아야 할 것 (리스크 방지)

- 버티컬별로 별도 Supabase 프로젝트를 만들지 않는다 (데이터 파편화, 마이그레이션 비용 2배 이상).
- 버티컬별로 컴포넌트를 복제(`AdminPageLesson.tsx` 같은 별도 파일)하지 않는다 — 설정 분기로
  해결되지 않는 요구가 생기면, 그건 진짜 새 기능이지 버티컬 분기가 아니다.
- 업종 문자열(`business_type`)을 직접 if 조건으로 참조하지 않는다 — 반드시
  `feature_flags`/`tenant_mode` 같은 정규화된 설정값을 경유한다(업종 목록이 바뀌어도
  기능 로직은 안 바뀌도록).

## 5. 단계별 로드맵

| 단계 | 내용 | 산출물 |
|---|---|---|
| Phase 1 | 기술 기반: `feature_flags` 스키마 추가, `AdminPage.tsx` 필터 확장, 버티컬 프리셋 구조 설계 | 마이그레이션 1건, 코드 변경 |
| Phase 2 | 레슨권 버티컬 랜딩페이지 제작 + 온보딩 딥링크 연결 (마케팅 자산 우선, 앱 자체는 Phase 1 결과물 그대로 사용) | 랜딩페이지, 카피, 광고 소재 |
| Phase 3 | 소규모 트래픽으로 전환율·활성화율 검증 (2~4주) | 지표 리포트 |
| Phase 4 | 검증되면 슈퍼관리자 콘솔에 버티컬 관리 UI 정식 추가, 2차 버티컬(학원) 착수 | 콘솔 기능, 2차 버티컬 기획 |

**Phase 1~2는 병행 가능** — 마케팅 자산 제작과 기능 플래그 개발이 서로 막지 않는다.
단, Phase 2의 "온보딩 시 자동 프리셋 적용"은 Phase 1 완료가 선행돼야 한다.

## 6. 리스크 / 트레이드오프

| 리스크 | 완화 방안 |
|---|---|
| 버티컬이 늘어날수록 마케팅 운영비(카피·광고·고객지원)가 곱으로 증가 | 처음엔 1개 버티컬만 검증 후 확장, 버티컬 간 랜딩 템플릿 재사용 |
| 코드가 "설정 분기"에서 "코드 분기"로 슬금슬금 변질(if 업종 하드코딩) | 코드리뷰 체크리스트에 "업종/버티컬 하드코딩 여부" 항목 추가 (CLAUDE.md 기존 체크리스트와 통합) |
| 한 조직이 여러 업종에 걸쳐 있는 경우 프리셋이 안 맞음 | 프리셋은 "기본값"일 뿐이며 조직관리자가 언제든 개별 오버라이드 가능하게 설계(이미 `tenant_mode`가 이 패턴을 씀) |
| 기존 범용 브랜드(DTS) 사용자에게 버티컬 마케팅이 혼란을 줄 수 있음 | 기존 가입 경로는 "범용 버티컬"(모든 기능 노출)로 유지, 신규 채널에서만 버티컬 딥링크 사용 |
| 버티컬 전환율이 기대보다 낮을 위험 | Phase 3 검증 단계를 짧게(2~4주) 두고 실패 시 다음 버티컬로 빠르게 피벗 |

## 7. 성공 지표 (KPI) 제안

- **마케팅**: 버티컬 랜딩페이지 전환율 (범용 랜딩 대비), 채널별 CAC(고객획득비용)
- **활성화**: 가입 후 4주 내 레슨권 1개 이상 등록 조직 비율
- **리텐션**: 버티컬 유입 조직의 3개월 유지율 (범용 유입 조직과 비교)
- **개발 효율**: 신규 버티컬 1개 추가에 걸리는 개발 리드타임(목표: 코드 변경 없이 설정만으로 1주 이내)
